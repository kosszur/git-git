git-push(1)
===========

NAME
----
git-push - Frissíti a remote referenciákat a hozzájuk tartozó objektumokkal együtt


SYNOPSIS
--------
[synopsis]
git push [--all | --branches | --mirror | --tags] [--follow-tags] [--atomic] [-n | --dry-run] [--receive-pack=<git-receive-pack>]
	 [--repo=<repository>] [-f | --force] [-d | --delete] [--prune] [-q | --quiet] [-v | --verbose]
	 [-u | --set-upstream] [-o <string> | --push-option=<string>]
	 [--[no-]signed | --signed=(true|false|if-asked)]
	 [--force-with-lease[=<refname>[:<expect>]] [--force-if-includes]]
	 [--no-verify] [<repository> [<refspec>...]]

DESCRIPTION
-----------
Frissít egy vagy több branchet, tag-et vagy más referenciát egy vagy több
remote repositoryban a lokális repositoryból, és elküld minden szükséges
adatot, ami még nincs meg a remote-on.

A push-olás legegyszerűbb módja a `git push <remote> <branch>`.
A `git push origin main` a lokális `main` branchet az `origin` nevű
remote `main` branchére push-olja.

Egy remote-csoport használatával egyszerre több remote-ra is push-olhatsz.
A remote-csoport a `remotes.<name>` beállításon keresztül konfigurált,
elnevezett remote-lista a git configban:

	$ git config remotes.all-remotes "origin gitlab backup"

Ekkor a `git push all-remotes` sorban push-ol az `origin`, a `gitlab` és
a `backup` remote-okra, mintha a `git push`-t mindegyikre külön-külön
futtattad volna. Minden remote a saját push-mapping konfigurációja
alapján, egymástól függetlenül kerül push-olásra. A konfigurációs
fájlban van egy `remotes.<group>` bejegyzés. (Lásd: linkgit:git-config[1]).

A `<repository>` argumentum alapértelmezetten a jelenlegi branch
upstreamje, vagy `origin`, ha nincs beállítva upstream.

Annak eldöntésére, hogy mely branchek, tagek vagy más referenciák
kerüljenek push-olásra, a Git a következő sorrendben dönt:

1. A `<refspec>` argumentum(ok) (például `main` a `git push origin main`
   parancsban), vagy a `--all`, `--mirror` vagy `--tags` kapcsolók
2. A push célpontjául szolgáló repository `remote.<name>.push` konfigurációja
3. A `push.default` konfiguráció. Az alapértelmezés `push.default=simple`,
   ami a jelenlegi branchhel megegyező nevű branchre push-ol.
   A `push.default`-ról bővebben lásd lent a <<CONFIGURATION,CONFIGURATION>> szakaszt.

Előfordulhat, hogy a `git push` hibával leáll, ha nincs beállítva
upstream a jelenlegi branchhez, attól függően, hogy mire van állítva a
`push.default`. Az upstreamek beállításáról és használatáról bővebben
lásd lent az <<UPSTREAM-BRANCHES,UPSTREAM BRANCHES>> szakaszt.

Érdekes dolgokat idézhetsz elő egy repositoryban minden alkalommal, amikor
push-olsz bele, ha 'hookokat' állítasz be ott. Lásd a
linkgit:git-receive-pack[1] dokumentációját.

[[OPTIONS]]
OPTIONS
-------
_<repository>_::
	A push célpontjául szolgáló "remote" repository. Ez a paraméter
	lehet egy URL (lásd lent a <<URLS,GIT URL-ek>> szakaszt), egy
	remote neve (lásd lent a <<REMOTES,REMOTES>> szakaszt),
	vagy egy remote-csoport neve
	(lásd lent a <<REMOTE-GROUPS,REMOTE GROUPS>> szakaszt).

`<refspec>...`::
	Megadja, melyik cél-refet melyik forrás-objektummal kell frissíteni.
+
A refspec formátuma `[+]<src>[:<dst>]`, például `main`,
`main:other`, vagy `HEAD^:refs/heads/main`.
+
Az _<src>_ gyakran a push-olandó lokális branch neve, de lehet
bármilyen tetszőleges "SHA-1 kifejezés" is (lásd linkgit:gitrevisions[7]).
+
Az _<dst>_ határozza meg, hogy a remote oldalon melyik ref frissüljön.
Egy branch, tag vagy más ref nevének kell lennie, nem egy tetszőleges
kifejezésnek.
+
A `+` opcionális, és ugyanazt csinálja, mint a `--force`.
+
A refspecet megírhatod a teljesen kifejtett formában (például
`refs/heads/main:refs/heads/main`), ami pontosan megadja a forrást és a
célt, vagy egy rövidebb formában (például `main` vagy
`main:other`). Az alábbiakban a refspecek kifejtésének szabályai
találhatók, valamint néhány egyéb speciális refspec-forma:
+
 *  Az _<src>_, `:<dst>` nélkül, ugyanazon ref frissítését jelenti, mint az
    _<src>_, hacsak a `remote.<repository>.push` konfiguráció más _<dst>_-t
    nem ad meg. Például ha a `main` egy branch, akkor a `main` refspec
    `main:refs/heads/main`-re fejtődik ki.
 *  Ha az _<dst>_ egyértelműen a <repository> remote egy refjére utal,
    akkor arra a refre fejtődik ki. Például ha a `v1.0` egy tag a
    remote-on, akkor a `HEAD:v1.0` a `HEAD:refs/tags/v1.0`-ra fejtődik ki.
 *  Ha az _<src>_ egy `refs/heads/`-szel vagy `refs/tags/`-szel kezdődő
    refre oldódik fel, akkor ezt kell a <dst> elé illeszteni. Például ha a
    `main` egy branch, akkor a `main:other` a `main:refs/heads/other`-re
    fejtődik ki.
 *  A speciális `:` refspec (vagy `+:` a non-fast-forward frissítések
    engedélyezéséhez) arra utasítja a Gitet, hogy "matching" brancheket
    push-oljon: minden branch esetén, amely a lokális oldalon létezik, a
    remote oldal frissül, ha ott már létezik ugyanolyan nevű branch.
 *  Az _<src>_ tartalmazhat egy `*` karaktert egy egyszerű mintaillesztés
    jelzésére. Ez úgy működik, mint egy glob, amely a mintára illeszkedő
    bármely refre illik. A `<src>`-ben és a `<dst>`-ben is csak egy `*`
    szerepelhet. Ez a refeket a * helyére a forrásból illeszkedő tartalom
    behelyettesítésével képezi le a célra. Például a
    `refs/heads/*:refs/heads/*` az összes branchet push-olja.
 *  A `^`-tal kezdődő refspec egy negatív refspec.
    Ez a kizárandó refeket adja meg. Egy ref akkor számít illeszkedőnek,
    ha legalább egy pozitív refspecre illeszkedik, és egyetlen negatív
    refspecre sem illeszkedik. A negatív refspecek lehetnek minta-refspecek.
    Ezeknek csak egy _<src>_-t szabad tartalmazniuk.
    A teljesen kiírt hex objektumnevek sem támogatottak.
    Például a `git push origin 'refs/heads/*' '^refs/heads/dev-*'`
    az összes branchet push-olja, kivéve a `dev-`-vel kezdődőket.
 *  Ha az _<src>_ üres, akkor törli a _<dst>_ refet a remote
    repositoryból. Például a `git push origin :dev` törli
    a `dev` branchet.
 *  A `tag <tag>` a `refs/tags/<tag>:refs/tags/<tag>`-ra fejtődik ki.
	Ez technikailag egy speciális szintaxis a `git push` számára, nem
	egy refspec, mivel a `git push origin tag v1.0` parancsban a `tag`
	és a `v1.0` argumentumok külön szerepelnek.
 *  Ha a refspec nem fejthető ki egyértelműen, hibával leáll, jelezve,
    hogy mit próbált meg, és az `advice.pushUnqualifiedRefname`
    konfigurációtól függően (lásd linkgit:git-config[1]) javaslatot tesz,
    melyik refs/ névtérbe szándékozhattál push-olni.

Nem minden frissítés engedélyezett: a részletekért lásd lent a PUSH RULES szakaszt.

`--all`::
`--branches`::
	Push-olja az összes branchet (azaz a `refs/heads/` alatti
	refeket); nem használható más <refspec>-cel együtt.

`--prune`::
	Eltávolítja azokat a remote brancheket, amelyeknek nincs lokális
	megfelelője. Például egy `tmp` nevű remote branch eltávolításra
	kerül, ha már nem létezik ugyanolyan nevű lokális branch. Ez a
	refspeceket is figyelembe veszi, pl. a
	`git push --prune remote refs/heads/*:refs/tmp/*` gondoskodik
	arról, hogy a remote `refs/tmp/foo` eltávolításra kerüljön, ha a
	`refs/heads/foo` nem létezik.

`--mirror`::
	Ahelyett, hogy a push-olandó refeket egyenként megneveznéd,
	megadja, hogy a `refs/` alatti összes ref (ami magában foglalja,
	de nem korlátozódik a `refs/heads/`, `refs/remotes/` és
	`refs/tags/` refekre) tükröződjön a remote repositoryba. Az
	újonnan létrehozott lokális refek push-olásra kerülnek a remote
	oldalra, a lokálisan frissített refek force update-elésre kerülnek
	a remote oldalon, a törölt refek pedig eltávolításra kerülnek a
	remote oldalról. Ez az alapértelmezett viselkedés, ha a
	`remote.<remote>.mirror` konfigurációs opció be van állítva.

`-n`::
`--dry-run`::
	Mindent elvégez, kivéve a frissítések tényleges elküldését.

`--porcelain`::
	Gépileg feldolgozható kimenetet állít elő. Az egyes refekhez
	tartozó állapotsor tabulátorral tagolt lesz, és a standard
	kimenetre kerül a standard hiba helyett. A refek teljes
	szimbolikus nevei jelennek meg.

`-d`::
`--delete`::
	Az összes felsorolt ref törlésre kerül a remote repositoryból. Ez
	ugyanaz, mintha minden ref elé kettőspontot tennél.

`--tags`::
	A `refs/tags` alatti összes ref push-olásra kerül, a
	parancssorban explicit módon megadott refspecek mellett.

`--follow-tags`::
	Push-olja az összes olyan refet, amely ezen opció nélkül is
	push-olásra kerülne, és emellett push-olja azokat az annotált
	tageket a `refs/tags` alatt, amelyek hiányoznak a remote-ról, de
	olyan commit-ish objektumra mutatnak, amely elérhető a push-olt
	refekből. Ez a `push.followTags` konfigurációs változóval is
	megadható. További információért lásd a `push.followTags`-t a
	linkgit:git-config[1]-ben.

`--signed`::
`--no-signed`::
`--signed=(true|false|if-asked)`::
	GPG-vel aláírja a push-kérést a fogadó oldalon frissítendő refekhez,
	hogy azt a hookok ellenőrizhessék, és/vagy naplózásra kerülhessen.
	A lehetséges értékek:
`false`;;
`--no-signed`;;
nem történik aláírási kísérlet.
`true`;;
`--signed`;;
a push meghiúsul, ha a szerver nem támogatja az aláírt push-olást.
`if-asked`;;
csak akkor ír alá, ha a szerver támogatja az aláírt push-olást. A push
akkor is meghiúsul, ha a `gpg --sign` tényleges hívása sikertelen. A
fogadó oldal részleteiért lásd a linkgit:git-receive-pack[1]-et.

`--atomic`::
`--no-atomic`::
	Atomi tranzakciót használ a remote oldalon, ha elérhető. Vagy
	minden ref frissül, vagy hiba esetén egyik ref sem frissül. Ha a
	szerver nem támogatja az atomi push-olást, a push meghiúsul.

`-o <option>`::
`--push-option=<option>`::
	Átküldi a megadott stringet a szervernek, amely azt továbbadja a
	pre-receive és a post-receive hooknak is. A megadott string nem
	tartalmazhat _NUL_ vagy _LF_ karaktert.
	Ha több `--push-option=<option>` is meg van adva, mindegyik
	elküldésre kerül a másik oldalra, a parancssorban felsorolt
	sorrendben.
	Ha a parancssorból nincs megadva `--push-option=<option>`,
	helyette a `push.pushOption` konfigurációs változó értékei
	kerülnek felhasználásra.

`--receive-pack=<git-receive-pack>`::
`--exec=<git-receive-pack>`::
	A 'git-receive-pack' program elérési útja a remote oldalon.
	Néha hasznos, ha ssh-n keresztül push-olsz egy remote
	repositoryba, és a program nincs benne az alapértelmezett
	`$PATH` valamelyik könyvtárában.

`--force-with-lease`::
`--no-force-with-lease`::
`--force-with-lease=<refname>`::
`--force-with-lease=<refname>:<expect>`::
	Általában a `git push` megtagadja egy olyan remote ref frissítését,
	amely nem őse a felülírásra használt lokális refnek.
+
Ez az opció felülbírálja ezt a korlátozást, ha a remote ref jelenlegi
értéke megegyezik a várt értékkel. Egyébként a `git push` meghiúsul.
+
Képzeld el, hogy rebase-elned kell azt, amit már publikáltál. Meg
kell kerülnöd a "kötelező fast-forward" szabályt, hogy az eredetileg
publikált történelmet lecserélhesd a rebase-elt történelemre. Ha
valaki más is épített az eredeti történelmedre, amíg rebase-eltél, a
branch csúcsa a remote-on előrehaladhatott az ő commitjával, és a
`--force`-szal történő vak push-olás elveszítené a munkáját.
+
Ez az opció lehetővé teszi, hogy jelezd: elvárod, hogy a frissítendő
történelem az legyen, amit rebase-eltél, és amelyet le akarsz
cserélni. Ha a remote ref még mindig a megadott commitra mutat,
biztos lehetsz benne, hogy senki más nem csinált semmit a reffel. Ez
olyan, mintha egy "lease"-t (bérletet) vennél fel a refre anélkül,
hogy explicit módon zárolnád, és a remote ref csak akkor frissül, ha
a "lease" még érvényes.
+
A `--force-with-lease` önmagában, a részletek megadása nélkül, minden
frissítendő remote refet véd azáltal, hogy megköveteli, hogy azok
jelenlegi értéke megegyezzen az azokhoz tartozó remote-tracking
branchünk értékével.
+
A `--force-with-lease=<refname>`, a várt érték megadása nélkül,
kizárólag az _<refname>_-t védi, ha az frissítésre kerülne, azáltal,
hogy megköveteli, hogy jelenlegi értéke megegyezzen az ahhoz tartozó
remote-tracking branchünk értékével.
+
A `--force-with-lease=<refname>:<expect>` kizárólag az _<refname>_-t
védi, ha az frissítésre kerülne, azáltal, hogy megköveteli, hogy
jelenlegi értéke megegyezzen a megadott _<expect>_ értékkel (amely
eltérhet az adott refnévhez tartozó remote-tracking branchünk
értékétől, sőt ilyen forma használatakor nem is kell, hogy legyen
ilyen remote-tracking branchünk). Ha az _<expect>_ egy üres string,
akkor a megnevezett ref még nem létezhet.
+
Vedd figyelembe, hogy minden forma, a `--force-with-lease=<refname>:<expect>`
kivételével, amely explicit módon megadja a ref várt jelenlegi
értékét, még kísérleti jellegű, és a szemantikájuk változhat, ahogy
tapasztalatot szerzünk ezzel a funkcióval kapcsolatban.
+
A `--no-force-with-lease` törli a parancssorban megelőzően megadott
összes `--force-with-lease`-t.
+
Egy általános biztonsági megjegyzés: ha ezt az opciót várt érték
nélkül adod meg, azaz `--force-with-lease` vagy
`--force-with-lease=<refname>` formában, az nagyon rosszul lép
kölcsönhatásba bármivel, ami a háttérben implicit módon `git fetch`-et
futtat a push célpontjául szolgáló remote-on, pl. egy `git fetch
origin` a repositorydon egy cronjobban.
+
A `--force`-hoz képest nyújtott védelem abban áll, hogy biztosítja,
hogy az olyan későbbi változtatások, amelyekre a munkád nem
támaszkodott, ne íródjanak felül, de ezt egy háttérfolyamat, amely a
háttérben refeket frissít, könnyedén meghiúsíthatja. Nincs más, csak
a remote-tracking információ, amire heurisztikaként támaszkodhatunk
azokhoz a refekhez, amelyeket feltehetően láttál, és amelyeket hajlandó
vagy felülírni.
+
Ha a szerkesztőd vagy valamilyen más rendszer a háttérben `git
fetch`-et futtat neked, ennek mérséklésére egy módszer, ha egyszerűen
felállítasz egy másik remote-ot:
+
----
git remote add origin-push $(git config remote.origin.url)
git fetch origin-push
----
+
Most, amikor a háttérfolyamat lefuttatja a `git fetch origin`-t, az
`origin-push`-on lévő referenciák nem frissülnek, így az olyan
parancsok, mint:
+
----
git push --force-with-lease origin-push
----
+
Meg fognak hiúsulni, hacsak nem futtatod le manuálisan a `git fetch
origin-push`-t. Ezt a módszert természetesen teljesen meghiúsítja
bármi, ami `git fetch --all`-t futtat, ebben az esetben vagy ki kell
kapcsolnod, vagy valami fáradságosabbat kell tenned, például:
+
----
git fetch              # update 'master' from remote
git tag base master    # mark our base point
git rebase -i master   # rewrite some commits
git push --force-with-lease=master:base master:master
----
+
Azaz hozz létre egy `base` taget az upstream kód azon verzióihoz,
amelyeket láttál, és amelyeket hajlandó vagy felülírni, majd írd át a
történelmet, végül force push-old a változtatásokat a `master`-re, ha
a remote verzió még mindig a `base`-nél tart, függetlenül attól, hogy
a lokális `remotes/origin/master` mire frissült a háttérben.
+
Alternatívaként, ha a `--force-if-includes`-t kiegészítő opcióként
adod meg a `--force-with-lease[=<refname>]` mellett (azaz anélkül,
hogy megmondanád, pontosan melyik commitra kell mutatnia a remote
oldali refnek, vagy hogy melyik refek vannak védve a remote oldalon),
akkor a "push" idején ellenőrzésre kerül, hogy a remote-tracking
refekből esetlegesen a háttérben implicit módon frissült
változtatások lokálisan integrálva lettek-e, mielőtt a force
frissítés engedélyezésre kerülne.

`-f`::
`--force`::
	Általában a `git push` megtagadja egy olyan branch frissítését,
	amely nem őse a push-olandó commitnak.
+
Ez a kapcsoló kikapcsolja ezt az ellenőrzést, a PUSH RULES szakaszban
lent leírt egyéb biztonsági ellenőrzéseket, valamint a
`--force-with-lease` ellenőrzéseit is. Emiatt a remote repository
elveszíthet commitokat; óvatosan használd.
+
Vedd figyelembe, hogy a `--force` az összes push-olt refre
vonatkozik, ezért ha `push.default` értéke `matching`, vagy a
`remote.<name>.push` több push célpontot is konfigurál, felülírhat a
jelenlegi branchtől eltérő refeket is (beleértve azokat a lokális
refeket, amelyek szigorúan lemaradva állnak a remote megfelelőjükhöz
képest). Ha csak egyetlen branchre akarsz force push-olni, tegyél egy
`+`-t a push-olandó refspec elé (pl. `git push origin +master` a
`master` branchre való force push-oláshoz). A részletekért lásd a
`<refspec>...` szakaszt fent.

`--force-if-includes`::
`--no-force-if-includes`::
	Csak akkor kényszerít frissítést, ha a remote-tracking ref
	csúcsa lokálisan integrálva lett.
+
Ez az opció egy olyan ellenőrzést kapcsol be, amely megvizsgálja, hogy
a remote-tracking ref csúcsa elérhető-e az átíráshoz alapul vett
lokális branch "reflog" bejegyzéseinek valamelyikéből. Az ellenőrzés
biztosítja, hogy a remote-ról érkező frissítések lokálisan be lettek
építve, azáltal, hogy elutasítja a force frissítést, ha ez nem
teljesül.
+
Ha az opció a `--force-with-lease` megadása nélkül kerül átadásra,
vagy a `--force-with-lease=<refname>:<expect>` mellett kerül
megadásra, akkor "no-op".
+
A `--no-force-if-includes` megadása kikapcsolja ezt a viselkedést.

`--repo=<repository>`::
	Ez az opció egyenértékű az _<repository>_ argumentummal. Ha
	mindkettő meg van adva, a parancssori argumentum élvez elsőbbséget.

`-u`::
`--set-upstream`::
	Minden naprakész vagy sikeresen push-olt branchhez hozzáad egy
	upstream (tracking) referenciát, amelyet az argumentum nélküli
	linkgit:git-pull[1] és más parancsok használnak. További
	információért lásd a `branch.<name>.merge`-t a
	linkgit:git-config[1]-ben.

`--thin`::
`--no-thin`::
	Ezek az opciók a linkgit:git-send-pack[1]-nek kerülnek átadásra. A
	thin transfer jelentősen csökkenti az elküldött adat mennyiségét,
	ha a küldő és a fogadó sok azonos objektumon osztozik. Az
	alapértelmezés a `--thin`.

`-q`::
`--quiet`::
	Elnyom minden kimenetet, beleértve a frissített refek listázását
	is, hacsak nem történik hiba. A folyamat állapota nem kerül
	jelentésre a standard hiba adatfolyamra.

`-v`::
`--verbose`::
	Bőbeszédűen fut.

`--progress`::
	A folyamat állapota alapértelmezetten a standard hiba
	adatfolyamra kerül jelentésre, ha az egy terminálhoz van
	csatolva, hacsak nincs megadva a `-q`. Ez a kapcsoló akkor is
	kikényszeríti a folyamat állapotának jelentését, ha a standard
	hiba adatfolyam nem terminálra van irányítva.

`--no-recurse-submodules`::
`--recurse-submodules=(check|on-demand|only|no)`::
	Arra használható, hogy biztosítsd, hogy a push-olandó revíziók
	által használt összes submodule-commit elérhető legyen egy
	remote-tracking branchen. A lehetséges értékek:
`check`;;
        A Git ellenőrizni fogja, hogy a push-olandó revíziókban
	módosult összes submodule-commit elérhető-e a submodule legalább
	egy remote-ján. Ha bármelyik commit hiányzik, a push megszakad,
	és nem nulla státuszkóddal lép ki.
`on-demand`;;
	az összes olyan submodule push-olásra kerül, amely módosult a
	push-olandó revíziókban. Ha az `on-demand` nem tudta push-olni
	az összes szükséges revíziót, szintén megszakad, és nem nulla
	státuszkóddal lép ki.
`only`;;
	az összes submodule push-olásra kerül, míg a szuperprojekt
	push-olatlan marad.
`no`;;
	felülbírálja a `push.recurseSubmodules` konfigurációs változót,
	ha nincs szükség submodule-rekurzióra. Hasonló a
	`--no-recurse-submodules` használatához.

+
Ha `on-demand`-ot vagy `only`-t használsz, és egy submodule-nak van
`push.recurseSubmodules=(on-demand|only)` vagy `submodule.recurse`
konfigurációja, további rekurzió történik. Ebben az esetben az `only`
`on-demand`-ként kezelendő.

`--verify`::
`--no-verify`::
	Be- vagy kikapcsolja a pre-push hookot (lásd linkgit:githooks[5]).
	Az alapértelmezés a `--verify`, amely esélyt ad a hooknak arra,
	hogy megakadályozza a push-t. A `--no-verify`-jal a hook teljesen
	megkerülésre kerül.

`-4`::
`--ipv4`::
	Csak IPv4-címeket használ, figyelmen kívül hagyva az IPv6-címeket.

`-6`::
`--ipv6`::
	Csak IPv6-címeket használ, figyelmen kívül hagyva az IPv4-címeket.

[[REMOTE-GROUPS]]
REMOTE GROUPS
-------------

A remote-csoport a `remotes.<name>` beállításon keresztül konfigurált,
elnevezett remote-lista a git configban:

	$ git config remotes.all-remotes "r1 r2 r3"

Ha egy csoportnév van megadva a `<repository>` argumentumként, a push
sorban végrehajtásra kerül a csoport minden egyes tagremote-jára. A
meghatározó elv:

	git push <options> all-remotes <args>

pontosan egyenértékű a következővel:

	git push <options> r1 <args>
	git push <options> r2 <args>
	...
	git push <options> rN <args>

ahol r1, r2, ..., rN az `all-remotes` tagjai. Nincs hozzáadva vagy
elvéve semmilyen speciális viselkedés — a csoport pusztán egy rövidítés
ugyanazon push parancs egyénileg történő futtatására minden egyes
tagremote-on.

Amikor egynél több remote-ból álló csoportra push-olsz, a Git egy
külön `git push` alfolyamatot indít minden egyes tagremote-hoz,
sorban. Minden alfolyamat ugyanazokat a kapcsolókat és refspeceket
kapja, mint az eredeti hívás. Ez azt jelenti, hogy a
`remote.<name>.push`-on keresztül konfigurált remote-onkénti
push-mappingek és a mirror mód (`remote.<name>.mirror`) egymástól
függetlenül kerülnek kiértékelésre minden egyes remote-nál, és egy
mirror remote a csoportban nem befolyásolhatja a csoport többi,
nem-mirror remote-jának push-viselkedését.

A `--atomic` opció nem támogatott csoportos push-oknál, mivel az
atomicitás csak egyetlen remote-hoz tartozó, egyetlen
transzportkapcsolaton belül garantálható. A Git hibával elutasítja a
hívást, ha a `--atomic` egy csoportnévvel kombinálva szerepel.

Ha bármelyik tagremote meghiúsul, akár egy push elutasítása miatt
(pl. egy non-fast-forward frissítés, egy szerveroldali hook, amely
elutasít egy refet), akár egy kapcsolódási hiba miatt (pl. a
repository nem létezik, a hitelesítés sikertelen, vagy a hálózat nem
elérhető), a Git jelenti a hibát, és folytatja a push-olást a csoport
fennmaradó remote-jaira. A teljes kilépési kód nem nulla, ha bármelyik
tag push-a meghiúsul.

Ez azt jelenti, hogy a felhasználó felelős azért, hogy az egyéni
push-ok sorrendje értelmes legyen. Ha a `git push r1` meghiúsulna egy
adott opció- és argumentumkészlettel, akkor a `git push all-remotes`
ugyanúgy meg fog hiúsulni, amikor eléri az r1-et. A csoportos push nem
tesz semmi különöset azért, hogy egy meghiúsuló egyéni push
sikeressé váljon.

OUTPUT
------

A "git push" kimenete a használt transzportmódszertől függ; ez a
szakasz a Git protokollon (akár lokálisan, akár ssh-n keresztül)
történő push-olás kimenetét írja le.

A push állapota táblázatos formában kerül kiírásra, minden sor egy
adott ref állapotát jelöli. Minden sor formátuma:

-------------------------------
 <flag> <summary> <from> -> <to> (<reason>)
-------------------------------

Ha a `--porcelain` van használva, akkor a kimenet minden sorának
formátuma:

-------------------------------
 <flag> \t <from>:<to> \t <summary> (<reason>)
-------------------------------

A naprakész refek állapota csak akkor jelenik meg, ha a `--porcelain`
vagy a `--verbose` opció van használva.

_<flag>_::
	Egyetlen karakter, amely jelzi a ref állapotát:
(space);; sikeresen push-olt fast-forward esetén;
`+`;; sikeres force update esetén;
`-`;; sikeresen törölt ref esetén;
`*`;; sikeresen push-olt új ref esetén;
`!`;; olyan ref esetén, amelyet elutasítottak, vagy nem sikerült push-olni; és
`=`;; olyan ref esetén, amely naprakész volt, és nem volt szükség push-olásra.

_<summary>_::
	Egy sikeresen push-olt ref esetén az összefoglaló megmutatja a
	ref régi és új értékét egy olyan formában, amely alkalmas a
	`git log` argumentumaként való felhasználásra (ez a legtöbb
	esetben `<old>..<new>`, forced non-fast-forward frissítéseknél
	pedig `<old>...<new>`).
+
Egy sikertelen frissítés esetén további részletek is megadásra
kerülnek:
+
--
rejected::
	A Git meg sem próbálta elküldeni a refet, jellemzően azért,
	mert az nem fast-forward, és nem force-oltad a frissítést.

remote rejected::
	A remote oldal elutasította a frissítést. Ezt általában egy
	hook okozza a remote oldalon, vagy az, hogy a remote
	repositoryn a következő biztonsági opciók valamelyike aktív:
	`receive.denyCurrentBranch` (a checkoutolt branchre történő
	push-oknál), `receive.denyNonFastForwards` (forced
	non-fast-forward frissítéseknél), `receive.denyDeletes` vagy
	`receive.denyDeleteCurrent`. Lásd linkgit:git-config[1].

remote failure::
	A remote oldal nem jelentette a ref sikeres frissítését,
	esetleg a remote oldali átmeneti hiba, a hálózati kapcsolat
	megszakadása vagy más átmeneti hiba miatt.
--

from::
	A push-olt lokális ref neve, a `refs/<type>/` előtag nélkül.
	Törlés esetén a lokális ref neve elmarad.

to::
	A frissítendő remote ref neve, a `refs/<type>/` előtag nélkül.

reason::
	Emberi nyelven megfogalmazott magyarázat. Sikeresen push-olt
	refeknél nincs szükség magyarázatra. Egy sikertelen ref esetén a
	hiba oka kerül leírásra.

PUSH RULES
----------

Biztonsági funkcióként a `git push` parancs csak bizonyos típusú
frissítéseket engedélyez, hogy megakadályozza az adatok véletlen
elvesztését a remote-on.

Mivel a branchek és a tagek eltérő célra szolgálnak, a branchre
push-olás biztonsági szabályai eltérnek a tagre push-olás
szabályaitól. Az alábbi szabályokban "frissítés" alatt minden
módosítást értünk, a törlések és létrehozások kivételével. A törlések
és létrehozások mindig engedélyezettek, kivéve, ha a konfiguráció
vagy a hookok megtiltják.

1. Ha a push célpontja egy **branch** (`refs/heads/*`): csak
   fast-forward frissítések engedélyezettek, ami azt jelenti, hogy a
   célpontnak a forráscommit ősének kell lennie. A forrásnak commitnak
   kell lennie.
2. Ha a push célpontja egy **tag** (`refs/tags/*`): minden frissítés
   elutasításra kerül. A forrás bármilyen objektum lehet.
3. Ha a push célpontja nem branch, sem tag:
   * Ha a forrás egy tree vagy blob objektum, minden frissítés
     elutasításra kerül.
   * Ha a forrás egy tag vagy commit objektum, bármilyen fast-forward
     frissítés engedélyezett, még olyan esetekben is, amikor az, ami
     fast-forwardolásra kerül, nem egy commit, hanem egy tag objektum,
     amely véletlenül egy olyan új commitra mutat, amely fast-forwardja
     az utolsó tagnek (vagy commitnak), amelyet lecserél. Egy tag
     teljesen más tagre cserélése is engedélyezett, ha ugyanarra a
     commitra mutat, csakúgy, mint egy peelelt tag push-olása, azaz a
     meglévő tag objektum által mutatott commit, vagy egy meglévő
     commit által mutatott új tag objektum push-olása.

Ezeket a szabályokat felülbírálhatod a `--force` megadásával, vagy az
opcionális vezető `+` hozzáadásával egy refspechez. Az egyetlen
kivétel, hogy semennyi force-olás sem fogja rávenni egy branchet, hogy
egy nem-commit objektumot elfogadjon, és a force-olás sem fogja rávenni
a remote repositoryt, hogy elfogadjon egy push-t, amelyet
konfigurációval megtiltottak elfogadni.

A hookok és a konfiguráció is felülbírálhatják vagy módosíthatják
ezeket a szabályokat, lásd pl. a `receive.denyNonFastForwards`-t és a
`receive.denyDeletes`-t a linkgit:git-config[1]-ben, valamint a
`pre-receive`-t és az `update`-et a linkgit:githooks[5]-ben.

NOTE ABOUT FAST-FORWARDS
------------------------

Amikor egy frissítés egy olyan branchet (vagy általánosabban egy
refet) módosít, amely korábban az A commitra mutatott, úgy, hogy az
egy másik, B commitra mutasson, akkor ezt fast-forward frissítésnek
nevezzük, ha és csak ha B az A leszármazottja.

Egy A-ból B-be történő fast-forward frissítésnél az a commitkészlet,
amelyre az eredeti A commit épült, részhalmaza azoknak a commitoknak,
amelyekre az új B commit épül. Ezért nem vész el semmilyen történelem.

Ezzel szemben egy non-fast-forward frissítés történelmet veszít el.
Például tegyük fel, hogy te és valaki más ugyanabból az X commitból
indultatok ki, és te egy B commithoz vezető történelmet építettél fel,
míg a másik személy egy A commithoz vezető történelmet épített. A
történelem így néz ki:

----------------

      B
     /
 ---X---A

----------------

Tegyük fel továbbá, hogy a másik személy már push-olta az A-hoz vezető
változtatásokat vissza abba az eredeti repositoryba, amelyből
mindketten megszereztétek az eredeti X commitot.

A másik személy által végzett push frissítette azt a branchet, amely
korábban az X commitra mutatott, úgy, hogy az A commitra mutasson. Ez
egy fast-forward.

De ha te próbálsz push-olni, akkor a branchet (amely most A-ra mutat)
próbálod a B committal frissíteni. Ez _nem_ fast-forward. Ha ezt
tennéd, az A commit által bevezetett változtatások elvesznének, mert
mindenki innentől B tetejére kezdene építeni.

A parancs alapértelmezetten nem engedélyez olyan frissítést, amely nem
fast-forward, hogy megelőzze a történelem ilyen elvesztését.

Ha nem akarod elveszíteni sem a saját munkádat (az X-től B-ig tartó
történelmet), sem a másik személy munkáját (az X-től A-ig tartó
történelmet), akkor először le kell fetchelned a történelmet a
repositoryból, létre kell hoznod egy olyan történelmet, amely mindkét
fél változtatásait tartalmazza, és vissza kell push-olnod az
eredményt.

Ezt megteheted a "git pull" futtatásával, az esetleges konfliktusok
feloldásával, majd az eredmény "git push"-olásával. A "git pull" létre
fog hozni egy C merge commitot az A és a B commitok között.

----------------

      B---C
     /   /
 ---X---A

----------------

Az A frissítése a kapott merge committal fast-forward lesz, és a
push-od elfogadásra kerül.

Alternatívaként rebase-elheted az X és B közötti változtatásodat A
tetejére a `git pull --rebase` segítségével, és push-olhatod vissza az
eredményt. A rebase létre fog hozni egy új, D commitot, amely az X és
B közötti változtatást A tetejére építi.

----------------

      B   D
     /   /
 ---X---A

----------------

Az A frissítése ezzel a committal ismét fast-forward lesz, és a
push-od elfogadásra kerül.

Van egy másik gyakori helyzet, amikor non-fast-forward elutasításba
ütközhetsz push-olás közben, és ez akkor is előfordulhat, amikor egy
olyan repositoryba push-olsz, amelybe rajtad kívül senki más nem
push-ol. Miután te magad push-oltad az A commitot (a szakasz első
ábráján), lecseréled azt a `git commit --amend`-del a B commit
előállítására, majd megpróbálod kipush-olni, mert elfelejtetted, hogy
az A-t már push-oltad. Ilyen esetben, és csak akkor, ha biztos vagy
benne, hogy időközben senki nem fetchelte le a korábbi A commitodat
(és nem kezdett rá építeni), lefuttathatod a `git push --force`-ot a
felülírásához. Más szóval, a `git push --force` egy olyan esetre
fenntartott módszer, amikor ténylegesen történelmet akarsz elveszíteni.


EXAMPLES
--------

`git push`::
	Úgy működik, mint a `git push <remote>`, ahol <remote> a
	jelenlegi branch remote-ja (vagy `origin`, ha a jelenlegi
	branchhez nincs remote konfigurálva).

`git push origin`::
	További konfiguráció nélkül a jelenlegi branchet push-olja a
	beállított upstreamre (`branch.<name>.merge` konfigurációs
	változó), ha annak neve megegyezik a jelenlegi branch nevével,
	egyébként hibával leáll, push-olás nélkül.
+
Ennek a parancsnak az alapértelmezett viselkedése, amikor nincs
megadva _<refspec>_, beállítható a remote `push` opciójának, vagy a
`push.default` konfigurációs változónak a beállításával.
+
Például, ha alapértelmezetten csak a jelenlegi branchet szeretnéd
push-olni az `origin`-re, használd a `git config remote.origin.push
HEAD`-et. Bármely érvényes _<refspec>_ (mint az alábbi példákban
szereplők) beállítható alapértelmezettként a `git push origin`
számára.

`git push origin :`::
	A "matching" brancheket push-olja az `origin`-re. A "matching"
	branchek leírásáért lásd az _<refspec>_-et fent, az
	<<OPTIONS,OPTIONS>> szakaszban.

`git push origin master`::
	Keresd meg a `master`-nek megfelelő refet a forrás repositoryban
	(legvalószínűbb, hogy a `refs/heads/master`-t találná meg), és
	frissítsd vele ugyanazt a refet (pl. `refs/heads/master`) az
	`origin` repositoryban. Ha a `master` nem létezett a remote-on,
	létrejönne.

`git push origin HEAD`::
	Kényelmes módja annak, hogy a jelenlegi branchet a remote-on
	ugyanolyan néven push-old.

`git push mothership master:satellite/master dev:satellite/dev`::
	Használd a `master`-nek megfelelő forrás refet (pl.
	`refs/heads/master`) a `satellite/master`-nek megfelelő ref
	frissítésére (legvalószínűbb, hogy `refs/remotes/satellite/master`)
	a `mothership` repositoryban; ugyanezt tedd a `dev` és a
	`satellite/dev` esetén is.
+
Az illesztési szemantika tárgyalásáért lásd a `<refspec>...`-t leíró
szakaszt fent.
+
Ez arra szolgál, hogy emulálja a `mothership`-en futtatott `git
fetch`-et az ellenkező irányban futtatott `git push` segítségével,
azért, hogy integrálja a `satellite`-en végzett munkát, és gyakran
szükséges, amikor a kapcsolat csak egy irányban hozható létre (azaz a
satellite tud ssh-zni a mothershipbe, de a mothership nem tud
kapcsolatot kezdeményezni a satellite-hoz, mert az utóbbi egy tűzfal
mögött van, vagy nem futtat sshd-t).
+
Miután lefuttattad ezt a `git push`-t a `satellite` gépen, ssh-znál a
`mothership`-be, és ott futtatnál egy `git merge`-et, hogy befejezd a
`mothership`-en futtatott `git pull` emulációját, amely a
`satellite`-en végzett változtatások lehúzására szolgált volna.

`git push origin HEAD:master`::
	A jelenlegi branchet push-olja a `master`-nek megfelelő remote
	refre az `origin` repositoryban. Ez a forma kényelmes a jelenlegi
	branch push-olására anélkül, hogy a lokális nevére kellene
	gondolnod.

`git push origin master:refs/heads/experimental`::
	Létrehozza az `experimental` branchet az `origin` repositoryban a
	jelenlegi `master` branch lemásolásával. Erre a formára csak
	akkor van szükség, ha egy új branchet vagy taget kell létrehozni a
	remote repositoryban, és a lokális név eltér a remote névtől;
	egyébként önmagában a ref neve is működik.

`git push origin :experimental`::
	Keresd meg az `experimental`-nak megfelelő refet az `origin`
	repositoryban (pl. `refs/heads/experimental`), és töröld azt.

`git push origin +dev:master`::
	Frissíti az origin repository master branchét a dev branchcsel,
	engedélyezve a non-fast-forward frissítéseket. *Ez a hivatkozás
	nélkül maradt commitokat hagyhat lógva az origin repositoryban.*
	Vedd figyelembe a következő helyzetet, ahol a fast-forward nem
	lehetséges:
+
----
	    o---o---o---A---B  origin/master
		     \
		      X---Y---Z  dev
----
+
A fenti parancs a következőre változtatná az origin repositoryt:
+
----
		      A---B  (unnamed branch)
		     /
	    o---o---o---X---Y---Z  master
----
+
Az A és B commitok többé nem tartoznának szimbolikus nevű branchhez,
így elérhetetlenné válnának. Emiatt ezeket a commitokat eltávolítaná
az origin repositoryn futtatott `git gc` parancs.
