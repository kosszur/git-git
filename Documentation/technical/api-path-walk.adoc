Path-Walk API
=============

A path-walk API az elérhető objektumok bejárására szolgál, de az
objektumokat kötegekben látogatja meg egy közös útvonal alapján, amelyben
megjelennek, vagy típus szerint.

Például az összes elérhető commit egy csoportban kerül meglátogatásra. Az
összes tag egy csoportban. Ezután az összes gyökérfa. Egy ponton az összes
blob, amely a `my/dir/to/A` útvonalon keresztül elérhető. Ha több lehetséges
útvonal is van ugyanahhoz az objektumhoz, akkor csak az egyiket használja
az objektum meglátogatásához.

[[_basics]]
Alapok
------

A path-walk API használatához illeszd be a `path-walk.h`-t, és hívd meg a
`walk_objects_by_path()`-t egy testreszabott `path_walk_info` structtal. A
struct arra szolgál, hogy beállítsd az összes opciót arra vonatkozóan,
hogyan haladjon a bejárás. Nézzük meg közelebbről a különböző opciókat és
használatukat.

`path_fn` and `path_fn_data`::
	A legfontosabb opció a `path_fn` opció, amely egy függvénymutató
	arra a visszahívásra, amely logikát tud végrehajtani a típus és
	útvonal szerint csoportosított objektumok objektumazonosítóin. Ez a
	függvény egy `data` értéket is kap, amely a `path_fn_data` tagnak
	felel meg, egyéni adatszerkezetek biztosítására ehhez a visszahívási
	függvényhez.

`revs`::
	Az elérhető objektumhalmaz pontos részleteinek konfigurálásához
	használd a `revs` tagot, és inicializáld a `revision.h`-beli
	revíziókezelő gépezettel. A `revs`-t olyan hívásokkal inicializáld,
	mint a `setup_revisions()` vagy a `parse_revision_opt()`. Ne hívd meg
	a `prepare_revision_walk()`-ot, mert azt a `walk_objects_by_path()`-en
	belül hívja meg.
+
Az is fontos, hogy ne add meg a `--objects` jelzőt a `revs` structhoz. A
revíziófeldolgozást csak commitok bejárására szabad használni, az
objektumokat pedig külön módon járja be ezen kiindulási commitok alapján.

`commits`::
`blobs`::
`trees`::
`tags`::
	Alapértelmezés szerint ezek a tagok engedélyezve vannak, és azt
	jelzik, hogy a path-walk API-nak meg kell hívnia a `path_fn`-t az
	ilyen típusú objektumokon. A speciális alkalmazások letilthatnak
	egyes opciókat, hogy egyszerűbb legyen az objektumok bejárása, vagy
	kevesebb legyen a `path_fn` hívás.
+
Vedd figyelembe, hogy a közvetlenül függőben lévő objektumként kért
objektumok (mint a könnyűsúlyú tagek vagy más ref-csúcsok céljai) mindig
kibocsátásra kerülnek a `path_fn`-hez, még akkor is, ha a megfelelő
típusjelző le van tiltva. Csak a fabejárás során felfedezett objektumokra
vonatkoznak ezek a típusszűrők. Ez biztosítja, hogy a revíziós bemeneten
keresztül kifejezetten kért objektumok soha ne essenek ki csendben.
+
Bár így lehetséges csak commitok bejárása, a fogyasztók jobban járnak, ha
inkább a revíziófeldolgozó API-t használják.

`prune_all_uninteresting`::
	Alapértelmezés szerint a path-walk API az összes elérhető útvonalat
	kibocsátja. Ez az opció lehetővé teszi a fogyasztók számára, hogy
	kijelentsék: nem érdeklik őket azok az útvonalak, ahol az összes
	tartalmazott objektum `UNINTERESTING` jelzővel van megjelölve. Ehhez
	a `boundary` opció használata szükséges a revíziófeldolgozásban, hogy
	a bejárás kibocsássa az `UNINTERESTING` jelzővel megjelölt commitokat.

`edge_aggressive`::
	Teljesítménybeli okokból általában csak a határ-commitokat tárja fel
	az UNINTERESTING objektumok megtalálásához. A sekély (shallow)
	klónok esetében azonban hasznos lehet az UNINTERESTING csúcs-commitokból
	elérhető összes fát és blobot UNINTERESTING-ként megjelölni. Ez
	megegyezik a `--objects-edge-aggressive` viselkedésével a revíziós
	API-ban.

`pl`::
	Ez a mintalista-mutató lehetővé teszi a path-walk keresés
	fókuszálását egy mintakészletre, csak a megadott mintákra illeszkedő
	útvonalakat bocsátva ki. A mintalistákról lásd a
	linkgit:gitignore[5] vagy a linkgit:git-sparse-checkout[1]
	részleteit. Ha a mintalista cone-mode mintákat használ, akkor a
	path-walk API metszheti a bejárt útvonalak halmazát a teljesítmény
	javítása érdekében.
