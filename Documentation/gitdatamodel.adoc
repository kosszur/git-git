gitdatamodel(7)
===============

NAME
----
gitdatamodel - A Git alapvető adatmodellje

SYNOPSIS
--------
gitdatamodel

DESCRIPTION
-----------

A Git használatához nem szükséges érteni a Git adatmodelljét, de nagyon
hasznos a Git dokumentációjának olvasásakor, hogy tudd, mit jelent, amikor a
dokumentáció „objektumot", „referenciát" vagy „indexet" említ.

A Git alapvető műveletei négyféle adatot használnak:

1. <<objects,Objektumok>>: commitok, tree-k, blobok és tag objektumok
2. <<references,Referenciák>>: branchek, tagek,
   remote-tracking branchek stb.
3. <<index,Az index>>, más néven a staging area
4. <<reflogs,Reflogok>>: a referenciák változásainak naplói („ref log")

[[objects]]
OBJECTS
-------

Egy Git repository összes commitja és fájlja „Git objektumként" tárolódik.
A Git objektumok a létrehozásuk után soha nem változnak, és minden
objektumnak van azonosítója, például
`1b61de420a21a2f1aaef93e38ecd0e45e8bc9f0a`.

Ez azt jelenti, hogy ha megvan egy objektum azonosítója, mindig
visszanyerheted a pontos tartalmát, amíg az objektumot nem törölték.

Minden objektumnak van:

[[object-id]]
1. egy *azonosítója* (más néven „objektumnév"), amely a típusának és
  tartalmának kriptográfiai hashe.
  Egy Git objektum az azonosítójával gyorsan kikereshető.
  Ezt általában hexadecimálisan ábrázolják, például
  `1b61de420a21a2f1aaef93e38ecd0e45e8bc9f0a`.
2. egy *típusa*. Négyféle objektum létezik:
   <<commit,commitok>>, <<tree,tree-k>>, <<blob,blobok>>
   és <<tag-object,tag objektumok>>.
3. *tartalma*. A tartalom szerkezete a típustól függ.

Így épül fel az egyes objektumtípusok szerkezete:

[[commit]]
commit::
    Egy commit a következő kötelező mezőket tartalmazza
    (bár vannak további, opcionális mezők is):
+
1. A repository adott verziójában lévő összes fájl teljes
   könyvtárszerkezete és az egyes fájlok tartalma, a commit legfelső szintű
   könyvtárának *<<tree,tree>>*-azonosítójaként tárolva
2. A *szülő commit(ok) azonosítója(i)*. Egy repository első commitjának 0
  szülője van, a rendes commitoknak 1, a merge commitoknak 2 vagy több
3. Egy *szerző* és a commit szerzőségének ideje
4. Egy *committer* és a commit commitolásának ideje
5. Egy *commit-üzenet*
+
Így tárolódik egy példa commit:
+
----
tree 1b61de420a21a2f1aaef93e38ecd0e45e8bc9f0a
parent 4ccb6d7b8869a86aae2e84c56523f8705b50c647
author Maya <maya@example.com> 1759173425 -0400
committer Maya <maya@example.com> 1759173425 -0400

Add README
----
+
Mint minden más objektum, a commitok sem változtathatók meg a
létrehozásuk után. Egy commit „amendelése" a `git commit --amend`
paranccsal például egy új, ugyanolyan szülőjű commitot hoz létre.
+
A Git nem tárolja egy commit diffjét: amikor a linkgit:git-show[1]
paranccsal kéred a commit megjelenítését, menet közben számítja ki a
diffet a szülőjéhez képest.

[[tree]]
tree::
    A Git egy tree-vel ábrázol egy könyvtárat.
    Fájlokat vagy további tree-ket (amelyek alkönyvtárak) tartalmazhat.
    A tree minden eleméhez felsorolja:
+
1. A *fájlnevet*, például `hello.py`
2. A *fájltípust*, amely az alábbi öt típus egyike kell hogy legyen:
  - *közönséges fájl*
  - *futtatható fájl*
  - *szimbolikus link*
  - *könyvtár*
  - *gitlink* (submodule-okhoz)
3. A <<object-id,*objektumazonosítót*>>, benne a fájl, könyvtár vagy gitlink
   tartalmával.
+
Így tárolódik például egy tree, amely egy könyvtárat (`src`) és egy fájlt
(`README.md`) tartalmaz:
+
----
100644 blob 8728a858d9d21a8c78488c8b4e70e531b659141f README.md
040000 tree 89b1d2e0495f66d6929f4ff76ff1bb07fc41947d src
----

NOTE: A fenti kimenetben a Git az egyes tree-bejegyzések fájltípusát olyan
formátumban jeleníti meg, amely lazán a Unix fájlmódokra épül (a `100644`
„közönséges fájl", a `100755` „futtatható fájl", a `120000` „szimbolikus
link", a `040000` „könyvtár", a `160000` pedig „gitlink"). Megjeleníti az
objektum típusát is: `blob` a fájlokhoz és szimbolikus linkekhez, `tree` a
könyvtárakhoz, `commit` pedig a gitlinkekhez.

[[blob]]
blob::
    Egy blob objektum egy fájl tartalmát tárolja.
+
Amikor commitolsz, a Git minden általad megváltoztatott fájl teljes
tartalmát blobként tárolja.
Ha például van egy commitod, amely 2 fájlt módosít egy 1000 fájlos
repositoryban, az a commit 2 új blobot hoz létre, a maradék 998 fájlhoz
pedig a korábbi blob-azonosítót használja.
Ez azt jelenti, hogy a commitok viszonylag kevés lemezterületet
használhatnak még egy nagyon nagy repositoryban is.

[[tag-object]]
tag object::
    A tag objektumok a következő kötelező mezőket tartalmazzák
    (bár vannak további, opcionális mezők is):
+
1. A hivatkozott objektum *azonosítója*
2. A hivatkozott objektum *típusa*
3. A *tagelő* és a tagelés dátuma
4. Egy *tag-üzenet*, hasonlóan a commit-üzenethez

Így tárolódik egy példa tag objektum:

----
object 750b4ead9c87ceb3ddb7a390e6c7074521797fb3
type commit
tag v1.0.0
tagger Maya <maya@example.com> 1759927359 -0400

Release version 1.0.0
----

NOTE: Az ebben a szakaszban szereplő összes példa a
`git cat-file -p <object-id>` paranccsal készült.

[[references]]
REFERENCES
----------

A referenciák segítségével nevet adhatunk egy commitnak.
Könnyebb megjegyezni, hogy „amin dolgozom, az a `turtle` branchen van", mint
azt, hogy „a változások a bb69721404348e commitban vannak".
A Git gyakran használja a „ref"-et a „reference" rövidítéseként.

A referenciák a következőkre hivatkozhatnak:

1. Egy objektumazonosítóra, általában egy <<commit,commit>> azonosítójára
2. Egy másik referenciára. Ezt „szimbolikus referenciának" nevezzük

A referenciák hierarchiában tárolódnak, és a Git eltérően kezeli a
referenciákat aszerint, hogy hol helyezkednek el a hierarchiában.
A legtöbb referencia a `refs/` alatt van. Íme a fő típusok:

[[branch]]
branches: `refs/heads/<name>`::
    Egy branch egy commit azonosítójára hivatkozik.
    Az a commit a branch legutóbbi commitja.
+
Egy branch commitjainak történetét úgy kapja meg a Git, hogy elindul a
commit azonosítójától, amelyre a branch hivatkozik, majd megnézi a commit
szülőjét (szülőit), a szülő szülőjét stb.

[[tag]]
tags: `refs/tags/<name>`::
    Egy tag egy commit azonosítójára, tag objektum azonosítójára vagy más
    objektumazonosítóra hivatkozik.
    Kétféle tag van:
    1. „Annotált tagek", amelyek egy <<tag-object,tag objektum>>
       azonosítójára hivatkoznak, amely egy tag-üzenetet tartalmaz
    2. „Könnyűsúlyú tagek", amelyek közvetlenül egy commit, blob vagy tree
       azonosítójára hivatkoznak
+
Bár a branchek és a tagek egyaránt egy commit azonosítójára hivatkoznak, a
Git nagyon eltérően kezeli őket.
A branchektől azt várjuk, hogy idővel változzanak: amikor commitolsz, a Git
frissíti az <<HEAD,aktuális branchedet>>, hogy az új commitra mutasson.
A tageket a létrehozásuk után általában nem változtatják meg.

[[HEAD]]
HEAD: `HEAD`::
    A `HEAD`-ben tárolja a Git az <<branch,aktuális branchedet>>, ha van
    aktuális branch. A `HEAD` a következők egyike lehet:
+
1. Szimbolikus referencia az aktuális branchedre, például `ref:
   refs/heads/main`, ha az aktuális branched a `main`.
2. Közvetlen referencia egy commit azonosítójára. Ebben az esetben nincs
   aktuális branch. Ezt „leválasztott HEAD-állapotnak" (detached HEAD state)
   nevezzük; bővebben lásd a DETACHED HEAD szakaszt a linkgit:git-checkout[1]
   oldalon.

[[remote-tracking-branch]]
remote-tracking branches: `refs/remotes/<remote>/<branch>`::
    Egy remote-tracking branch egy commit azonosítójára hivatkozik.
    Így tárolja a Git egy remote repository-beli branch utoljára ismert
    állapotát. A `git fetch` frissíti a remote-tracking brancheket. Amikor a
    `git status` azt mondja, hogy „you're up to date with origin/main",
    akkor ezt nézi.
+
A `refs/remotes/<remote>/HEAD` egy szimbolikus referencia a remote
alapértelmezett branchére. Ezt a branchet checkoutolja a `git clone`
alapértelmezés szerint.

[[other-refs]]
Egyéb referenciák::
    A Git eszközök bárhol létrehozhatnak referenciákat a `refs/` alatt.
    Például a linkgit:git-stash[1], a linkgit:git-bisect[1] és a
    linkgit:git-notes[1] mind saját referenciákat hoz létre a
    `refs/stash`, `refs/bisect` stb. helyeken.
    Harmadik féltől származó Git eszközök szintén létrehozhatnak saját
    referenciákat.
+
A Git a `HEAD`-en kívül is létrehozhat referenciákat a hierarchia alján,
például az `ORIG_HEAD`-et.

NOTE: A Git törölhet olyan objektumokat, amelyek egyetlen referenciából vagy
<<reflogs,reflogból>> sem „elérhetők".
Egy objektum „elérhető", ha megtaláljuk úgy, hogy követjük a tageket ahhoz,
amit tagelnek, a commitokat a szüleikhez vagy fáikhoz, a fákat pedig az
általuk tartalmazott fákhoz vagy blobokhoz.
Ha például amendelsz egy commitot a `git commit --amend` paranccsal, többé
nem lesz olyan branch, amely a régi commitra mutat.
A régi commitot az aktuális branch <<reflogs,reflogja>> rögzíti, így még
mindig „elérhető", de amikor a reflog-bejegyzés lejár, elérhetetlenné
válhat, és törlődhet.
Az elérhető objektumok soha nem törlődnek.

[[index]]
THE INDEX
---------
Az index, más néven a „staging area", fájlok listája és az egyes fájlok
tartalma, <<blob,blobként>> tárolva.
Fájlokat a linkgit:git-add[1] paranccsal adhatsz az indexhez, vagy
frissítheted egy indexbeli fájl tartalmát. Ezt a fájl commithoz való
„stage-elésének" nevezzük.

Egy <<tree,tree>>-vel ellentétben az index fájlok lapos listája.
Amikor commitolsz, a Git az indexbeli fájllistát könyvtár-<<tree,tree>>-vé
alakítja, és azt a fát használja az új <<commit,commitban>>.

Minden indexbejegyzésnek 4 mezője van:

1. A *fájltípus*, amely a következők egyike kell hogy legyen:
  - *közönséges fájl*
  - *futtatható fájl*
  - *szimbolikus link*
  - *gitlink* (submodule-okhoz)
2. A fájl *<<blob,blob>>*-azonosítója,
   vagy (ritkán) a submodule *<<commit,commit>>*-azonosítója
3. A *stage-szám*, amely 0, 1, 2 vagy 3. Ez általában 0, de ha merge
   konfliktus van, ugyanabból a fájlnévből több verzió is lehet az
   indexben.
4. A *fájlútvonal*, például `src/hello.py`

Rendkívül ritka, hogy közvetlenül az indexet nézzük: az ember általában a
`git status`-t futtatja, hogy lássa az index és a <<HEAD,HEAD>> közti
változások listáját.
De a `git ls-files --stage` paranccsal megtekintheted az indexet.
Íme a `git ls-files --stage` kimenete egy 2 fájlos repositoryban:

----
100644 8728a858d9d21a8c78488c8b4e70e531b659141f 0 README.md
100644 665c637a360874ce43bf74018768a96d2d4d219a 0 src/hello.py
----

[[reflogs]]
REFLOGS
-------

Valahányszor egy branch, remote-tracking branch vagy a HEAD frissül, a Git
frissít egy „reflog" nevű naplót az adott <<references,referenciához>>.
Ez azt jelenti, hogy ha hibázol, és „elveszítesz" egy commitot, általában
visszanyerheted a commit azonosítóját a `git reflog <reference>`
futtatásával.

A reflog naplóbejegyzések listája. Minden bejegyzésben van:

1. A *commit azonosítója*
2. *Időbélyeg* arról, mikor történt a változás
3. *Naplóüzenet*, például `pull: Fast-forward`

A reflogok csak a lokális repositoryban végzett változásokat naplózzák.
Ezek nem oszlanak meg a remote-okkal.

Egy reflogot a `git reflog <reference>` paranccsal tekinthetsz meg.
Íme például egy kétszer módosult `main` branch reflogja:

----
$ git reflog main --date=iso --no-decorate
750b4ea main@{2025-09-29 15:17:05 -0400}: commit: Add README
4ccb6d7 main@{2025-09-29 15:16:48 -0400}: commit (initial): Initial commit
----
