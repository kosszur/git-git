git-hook(1)
===========

NAME
----
git-hook - Git hookok futtatása

SYNOPSIS
--------
[verse]
'git hook' run [--allow-unknown-hook-name] [--ignore-missing] [--to-stdin=<path>] [(-j|--jobs) <n>]
	<hook-name> [-- <hook-args>]
'git hook' list [--allow-unknown-hook-name] [-z] [--show-scope] <hook-name>

DESCRIPTION
-----------

Parancsfelület Git hookok futtatásához (lásd linkgit:githooks[5]), amelyet
más szkriptelt Git-parancsok használhatnak.

Ez a parancs az alapértelmezett konfigurációs fájlokban ilyen
config-halmazokat elemez:

  [hook "linter"]
    event = pre-commit
    command = ~/bin/linter --cpp20

Ebben a példában a `[hook "linter"]` egy szkriptet képvisel – `~/bin/linter
--cpp20` –, amely megosztható sok repo, sőt sok hook-esemény között is, ha
ez helyénvaló.

Egy nem kapcsolódó hook hozzáadásához, amely egy másik eseményen fut,
például egy helyesírás-ellenőrzőt a commit-üzeneteidhez, ilyen
konfigurációt írnál:

  [hook "linter"]
    event = pre-commit
    command = ~/bin/linter --cpp20
  [hook "spellcheck"]
    event = commit-msg
    command = ~/bin/spellchecker

Ezzel a konfigurációval, amikor lefuttatod a 'git commit'-ot, először a
`~/bin/linter --cpp20` kapja meg a lehetőséget, hogy ellenőrizze a
commitolandó fájljaidat (a `pre-commit` hook-esemény során), majd a
`~/bin/spellchecker` kapja meg a lehetőséget, hogy ellenőrizze a
commit-üzenetedet (a `commit-msg` hook-esemény során).

A parancsok abban a sorrendben futnak, ahogy a Git a hozzájuk tartozó
`hook.<friendly-name>.event` configokkal találkozik a konfiguráció
elemzése során (lásd linkgit:git-config[1]). Bár több `hook.linter.event`
config is hozzáadható, csak egy `hook.linter.command` esemény érvényes – a
Git "az utolsó nyer" elvet használja annak eldöntésére, melyik parancsot
futtassa.

Tehát ha azt szeretnéd, hogy a lintered fusson commitoláskor és
pusholáskor is, így konfigurálnád:

  [hook "linter"]
    event = pre-commit
    event = pre-push
    command = ~/bin/linter --cpp20

Ezzel a konfigurációval a `~/bin/linter --cpp20`-t a Git egy commit
generálása előtt (a `pre-commit` során), valamint egy push végrehajtása
előtt (a `pre-push` során) futtatná.

És ha a lintered mellett egy titokszivárgás-detektort is futtatni akarnál
csak a "pre-commit" hook-esemény során, ehelyett így konfigurálnád:

  [hook "linter"]
    event = pre-commit
    command = ~/bin/linter --cpp20
  [hook "no-leaks"]
    event = pre-commit
    command = ~/bin/leak-detector

Ezzel a konfigurációval, egy commit generálása előtt (a `pre-commit`
során), a Git először a `~/bin/linter --cpp20`-t indítaná el, másodszor
pedig a `~/bin/leak-detector`-t. Mindegyik kimenetét kiértékelné annak
eldöntésekor, hogy folytassa-e a commitolást.

A hook-események teljes listájáért, amelyekre a
`hook.<friendly-name>.event`-et beállíthatod, és arról, hogyan hívódnak
meg a hookok ezen események során, lásd a linkgit:githooks[5] oldalt.

A Git figyelmen kívül hagy minden olyan `hook.<friendly-name>.event`-et,
amely olyan eseményt ad meg, amelyet nem ismer fel. Ez szándékos, hogy a
Gitet becsomagoló eszközök használhassák a hook-infrastruktúrát a saját
hookjaik futtatására; további útmutatásért lásd a "WRAPPERS" szakaszt.

Általánosságban, amikor az utasítások azt javasolják, hogy adj hozzá egy
szkriptet a `.git/hooks/<hook-event>`-hez, ehelyett megadhatod a
configban a következő futtatásával:

----
git config set hook.<some-name>.command <path-to-script>
git config set --append hook.<some-name>.event <hook-event>
----

Így megoszthatod a szkriptet több repo között. Azaz a `cp
~/my-script.sh ~/project/.git/hooks/pre-commit` ezzé válna:

----
git config set hook.my-script.command ~/my-script.sh
git config set --append hook.my-script.event pre-commit
----

SUBCOMMANDS
-----------

run::
	Az `<hook-name>`-hez konfigurált hookokat futtatja, abban a
	sorrendben, ahogy a config elemzése során felfedezi őket. A
	hookdirből származó alapértelmezett `<hook-name>` fut utoljára. A
	támogatott hook-nevekért lásd a linkgit:githooks[5] oldalt.
+

A hook pozicionális argumentumait egy kötelező `--` (vagy
`--end-of-options`, lásd linkgit:gitcli[7]) után kell átadni. Arról, hogy
a hookok milyen argumentumokra számíthatnak (ha vannak ilyenek), lásd a
linkgit:githooks[5] oldalt.

list [-z] [--show-scope]::
	Kiírja azoknak a hookoknak a listáját, amelyek a `<hook-name>`
	eseményen lefutnak. Ha ahhoz az eseményhez nincs hook konfigurálva,
	figyelmeztetést ír ki, és 1-et ad vissza.
	A `-z`-vel a kimeneti sorokat NUL-lal zárja le sortörés helyett.

OPTIONS
-------

--allow-unknown-hook-name::
	Alapból a `git hook run` és a `git hook list` kilép, ha a
	`<hook-name>` nem a Git által ismert hook-esemény (az ismert hookok
	listájáért lásd linkgit:githooks[5]). Ez az olyan elgépelések
	elkapásában segít, mint a `prereceive`, amikor a `pre-receive` volt a
	szándék. Add meg ezt a kapcsolót az ismeretlen hook-nevek
	engedélyezéséhez.

--to-stdin::
	A "run"-hoz; megad egy fájlt, amely a hook stdinjébe lesz
	streamelve. A hook a teljes fájlt megkapja az elejétől az EOF-ig.

--ignore-missing::
	Minden hiányzó hook figyelmen kívül hagyása csendben nulla
	visszaadásával. Olyan eszközökhöz, amelyek egy esetleg jelen lévő,
	esetleg nem, hook vak, egyszeri futtatását akarják elvégezni.

-z::
	A "list" kimeneti sorainak lezárása NUL-lal sortörés helyett.

--show-scope::
	A "list"-hez; minden konfigurált hook felhasználóbarát neve elé egy
	tabbal elválasztott config-hatókört tesz (pl. `local`, `global`,
	`system`), a `git config --show-scope` kimeneti stílusát követve. A
	hookdirből származó hagyományos hookokat ez nem érinti.

-j::
--jobs::
	Csak a `run`-hoz érvényes.
+
Megadja, hány hook fusson egyidejűleg. Ha ez a kapcsoló nincs megadva, a
`hook.jobs` config értéke lesz használva, lásd linkgit:git-config[1]. Ha
egyik sincs megadva, az alapértelmezés 1 (soros végrehajtás).
+
Ha 1-nél nagyobb, felülírja a hookonkénti `hook.<friendly-name>.parallel`
beállítást, lehetővé téve, hogy az esemény összes hookja egyszerre
fusson, még akkor is, ha egyenként nincsenek párhuzamosként megjelölve.
+
Néhány hook mindig sorban fut, függetlenül ettől a kapcsolótól vagy a
`hook.jobs` configtól, mert a Git tudja, hogy nem tudnak biztonságosan
párhuzamosan futni: `applypatch-msg`, `pre-commit`, `prepare-commit-msg`,
`commit-msg`, `post-commit`, `post-checkout` és `push-to-checkout`.

WRAPPERS
--------

A `git hook run`-t úgy tervezték, hogy a Gitet becsomagoló eszközök
számára megkönnyítse a hookok konfigurálását és végrehajtását a Git
hook-infrastruktúrájával. Lehetséges argumentumokat és stdint megadni a
parancssoron keresztül, valamint párhuzamos vagy soros végrehajtást
megadni, ha a felhasználó több hookot adott meg.

Feltételezve, hogy a csomagolód egy "mywrapper-start-tests" nevű hookot
akar támogatni, a felhasználóiddal így adathatod meg a hookjaikat:

  [hook "setup-test-dashboard"]
    event = mywrapper-start-tests
    command = ~/mywrapper/setup-dashboard.py --tap

Ezután a 'mywrapper' eszközödben bármely felhasználó konfigurált hookjait
meghívhatod a következő futtatásával:

----
git hook run --allow-unknown-hook-name mywrapper-start-tests \
  # providing something to stdin
  --stdin some-tempfile-123 \
  # execute multiple hooks in parallel
  --jobs 3 \
  # plus some arguments of your own...
  -- \
  --testname bar \
  baz
----

Ügyelj arra, hogy a csomagolód hook-eseményeit úgy nevezd el, hogy
valószínűtlenül fedjenek át a Git natív hookjaival (lásd
linkgit:githooks[5]) – egy `mywrappertool-validate-commit` nevű
hook-eseményt sokkal kevésbé valószínű, hogy hozzáadnak a natív Githez,
mint egy `validate-commit` nevű hook-eseményt. Ha a Git elkezd egy olyan
hook-eseményt használni, amelynek ugyanaz a neve, mint a csomagoló
hookodnak, a felhasználóid hookjait nem szándékolt és nem támogatott
módon hívhatja meg.
